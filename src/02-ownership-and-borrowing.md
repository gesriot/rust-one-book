# Глава 2. Владение и заимствование

Рассмотрим такой C-код:

```c
static char *g_buffer = NULL;
static size_t g_len = 0;

void writer(const char *msg) {
    free(g_buffer);
    g_buffer = malloc(strlen(msg) + 1);
    strcpy(g_buffer, msg);
    g_len = strlen(msg);
}

void reader(void) {
    if (g_buffer != NULL) {
        fwrite(g_buffer, 1, g_len, stdout);
    }
}
```

Двадцать строк, на первый взгляд ничего особенного. В однопоточной программе это работало бы безупречно: `writer` создаёт буфер и пишет в него длину, `reader` читает. Запусти эту пару в двух потоках без блокировок – и получишь весь набор: use-after-free (`free` в `writer` пересекается с чтением в `reader`), data race на `g_buffer` и `g_len`, рассогласование между указателем и длиной (`g_buffer` уже новый, `g_len` ещё старый – `reader` уходит читать за конец нового буфера), неопределённое поведение в самой широкой формулировке.

Эта программа существует не из-за невнимательности автора. Она существует потому, что язык позволил.

Конкретно – вот где ложь. Функция `writer`, заканчиваясь, оставляет в глобальной памяти неявное утверждение: «если кто-то увидит `g_buffer != NULL`, он может прочитать оттуда `g_len` байт». Это утверждение в общем случае неправда. Оно становится правдой только при определённой дисциплине внешнего вызова – например, под общим mutex'ом – но дисциплина в языке не записана. Утверждение остаётся в коде в лучшем случае в виде комментария. Программа собирается и до поры работает.

И это не экзотика, а типичная анатомия нетривиального бага. И у него есть один неприятный признак: он не воспроизводится по запросу.

Данная глава – про инструмент, который такое не скомпилирует.

Чтобы это работало, языку нужен способ записывать в коде утверждения о владении и проверять их. Этот способ называется ownership.

Ownership в Rust – это не бизнес-владение и не моральная категория; это тройка фактов о каждом значении: кто за него отвечает, как долго оно живёт и кто имеет к нему доступ в каждый момент времени. Эти факты записаны в системе типов и проверяются компилятором. Программа, в которой эти факты противоречивы, не собирается; программа, в которой они согласованы, гарантированно не содержит конкретного класса ошибок. Никакой философии, runtime-проверок, и сборщика мусора. Три правила и компилятор, который их обеспечивает.

## Один владелец на ресурс

Любое значение в Rust в любой момент времени принадлежит ровно одной переменной. Эта переменная называется владельцем (owner). Когда она уходит из области видимости – заканчивается функция, заканчивается блок – значение освобождается. Прямо здесь и сейчас, в этой точке кода. Если внутри значения была память – она возвращается аллокатору. Если был открытый файловый дескриптор – он закрывается. Если был сокет – закрывается. Это называется RAII (Resource Acquisition Is Initialization). В Rust этот принцип применяется ко всем типам без исключения.

Простейший пример:

```rust
fn main() {
    let s = String::from("hello");
    // s – владелец строки "hello"
}   // здесь s выходит из scope, и память строки освобождается
```

Освобождение случилось ровно в той точке, где закрылась фигурная скобка. Эта точка известна на этапе компиляции – компилятор видит её в исходном коде. Поэтому код освобождения вставляется в бинарник на этапе сборки. Никаких runtime-проверок, никакого сборщика мусора, никаких пауз. Память освобождается автоматически, но детерминированно — эти два слова обычно стоят в разных предложениях, и Rust держит их в одном. Это устраняет целый класс багов одним структурным решением, а не дисциплиной программиста.

Освобождение в этой точке настраиваемо. Любой тип может реализовать трейт `Drop` — указать, что должно произойти, когда значение уходит из жизни. Для `String` это `free` для буфера в куче. Для `File` — закрытие дескриптора. Для `MutexGuard` (это уже Глава 8) — отпускание мьютекса. Для собственного типа `DatabaseConnection` ты можешь написать `Drop`, который вернёт соединение в пул. Каждый раз, когда переменная такого типа выходит из scope, ровно эта логика выполняется. Без вызова из кода. Без шанса забыть.

Организм управляет ресурсами по тому же принципу: у каждого ресурса один владелец, смерть владельца освобождает ресурс, передача требует явного механизма. Биологи называют это морфостазом. Rust называет это borrow checker.

Если значение нужно передать другой функции, есть два варианта. Первый — отдать. Второй — одолжить. Выбор между ними не косметический; он определяет, кто несёт ответственность за освобождение и кто имеет право читать.

```rust
fn take(s: String) {
    println!("{}", s);
}   // здесь s — теперь её владелец take — выходит из scope, строка освобождается

fn main() {
    let s = String::from("hello");
    take(s);
    // s здесь больше не существует — её владельца больше нет
}
```

После `take(s)` переменная `s` в `main` недоступна. Не потому, что компилятор «такое не любит», а потому, что значения больше нет — оно ушло во владение к `take` и было уничтожено вместе с её фреймом. Если попробуешь использовать `s` после этой строки, компилятор откажет:

```
error[E0382]: borrow of moved value: `s`
```

«Borrow of moved value» — заимствование перемещённого значения. Это та ошибка, которую новички в Rust видят чаще всего, и обычно её первая реакция — «что за странность, почему я не могу пользоваться переменной». Странности здесь нет. Ты отдал значение. У тебя его больше нет. Это честное правило, и компилятор его честно соблюдает. (Да, компилятор был прав. Снова.)

## Move

Такая передача владения называется move. Никакого нового аллока в куче не происходит: указатель на блок памяти, длина и capacity просто переходят в новую переменную, а сама строка остаётся на старом месте. Меняется только владелец.

Присваивание (или передача в функцию, или возврат из функции) перемещает владение. Оригинал перестаёт существовать; теперь владелец — новый.

```rust
let a = String::from("hello");
let b = a;            // владение перешло от a к b
println!("{}", a);    // ошибка компиляции: a больше не владеет ничем
```

Именно здесь спотыкаются дольше всего. Это не каприз дизайнеров, а формализация того, что про каждое присваивание и так нужно знать: копирует ли оно данные или создаёт новое имя для тех же. В Rust ответ виден из синтаксиса: либо явный `clone` (копирование), либо move (передача).

Если тебе всё-таки нужна копия, пишешь явно:

```rust
let a = String::from("hello");
let b = a.clone();    // явная копия — выделяется новая память, копируются байты
println!("{}", a);    // работает, a всё ещё владеет своей строкой
println!("{}", b);    // и b владеет своей
```

`.clone()` — обычная операция, никакой магии в ней нет; для `String` она вызывает `malloc` и копирует содержимое. Это явно платный вызов, и хорошо, что он явно платный — в коде сразу видно, где деньги тратятся.

С маленькими типами Rust ведёт себя чуть иначе. Числа, символы, булевы, кортежи из чисел — это типы, реализующие специальный трейт `Copy`. Для них присваивание не move, а copy: бит-в-бит копирование значения. Никакой кучи, никакого освобождения, никакой сложности.

```rust
let x = 5;
let y = x;       // копия — теперь два независимых i32
println!("{}", x);  // работает
```

Граница между Copy-типами и не-Copy типами проста: всё, что не управляет ресурсом снаружи себя (память в куче, файловый дескриптор, сокет), может быть `Copy`. Всё, что управляет, — не может, потому что бит-в-бит копирование указателя в кучу создало бы двух владельцев одного блока, а двух владельцев у нас не бывает.

Здесь полезно остановиться и посмотреть, как `Drop` работает на практике. Объявим тип, который что-то говорит при освобождении:

```rust
struct Resource {
    name: String,
}

impl Drop for Resource {
    fn drop(&mut self) {
        println!("освобождаю {}", self.name);
    }
}

fn main() {
    let a = Resource { name: "A".into() };
    {
        let b = Resource { name: "B".into() };
        println!("внутри блока");
    }   // здесь b выходит из scope — печатается "освобождаю B"
    println!("снаружи блока");
}       // здесь a выходит из scope — печатается "освобождаю A"
```

Вывод программы:

```
внутри блока
освобождаю B
снаружи блока
освобождаю A
```

Порядок освобождения — обратный порядку создания внутри одного scope, и точки освобождения — это закрывающиеся фигурные скобки. Это полностью предсказуемо. В реальной программе вместо `println!` в `drop` стоит `close` для файла, `release` для блокировки, `disconnect` для сетевого соединения. Освобождение ресурса гарантировано даже если функция упадёт в panic в середине: `Drop` вызывается при разворачивании стека (unwind).

Передача владения работает в обе стороны. Когда функция возвращает значение, владение тоже переходит — теперь от функции к её вызывающему:

```rust
fn make_greeting(name: &str) -> String {
    let mut s = String::from("Привет, ");
    s.push_str(name);
    s
}

fn main() {
    let g = make_greeting("мир");   // владение строкой переходит в g
    println!("{}", g);
}                                    // здесь g выходит из scope, строка освобождается
```

Никаких лишних копирований. `String`, созданная внутри `make_greeting`, не копируется при возврате — у неё просто меняется владелец. Фактически происходит перемещение трёх машинных слов (указатель, длина, capacity) — операция, не зависящая от размера самой строки. На уровне ассемблера разницы между «вернуть `String`» и «вернуть указатель» практически нет.

На первый взгляд передача владения выглядит ограничением. На самом деле это формализация того, что компилятор всегда точно знает, кто должен освобождать ресурс: освобождает тот, кто владеет, а владеет в каждый момент времени ровно один.

## Borrow

Если бы у нас был только move, программирование на Rust превратилось бы в мучение. Каждый вызов функции означал бы потерю значения; чтобы продолжить работать с данными, их пришлось бы либо клонировать перед вызовом, либо принимать значение обратно из функции. К счастью, у передачи владения есть естественная пара — механизм, который даёт временный доступ к значению, не забирая его насовсем. Это заимствование (borrowing).

Заимствовать — значит дать функции временный доступ к значению, не передавая владение. В коде это выглядит так:

```rust
fn length(s: &String) -> usize {
    s.len()
}

fn main() {
    let s = String::from("hello");
    let n = length(&s);     // даём временный read-only доступ
    println!("{} символов в '{}'", n, s);  // s всё ещё наша
}
```

`&s` — это ссылка (reference) на `s`. Тип параметра `&String` означает: «я не владею, я только смотрю». Когда функция возвращается, ссылка перестаёт существовать; владелец остался на месте.

Бывает два вида ссылок:

- `&T` — неизменяемая (shared) ссылка. Можно читать, нельзя менять.
- `&mut T` — изменяемая (exclusive) ссылка. Можно и читать, и менять.

И вокруг них — главное правило borrow checker, ради которого вся эта глава пишется:

> В каждый момент времени для одного значения может существовать **либо** сколько угодно неизменяемых ссылок (`&T`), **либо** ровно одна изменяемая (`&mut T`). Третьего не дано.

Это правило — формализация дисциплины, которую опытные системные программисты годами держат в голове как «не давай ссылку на изменяемый объект, пока кто-то ещё его читает». Без borrow checker это конвенция; в Rust — закон, проверяемый компилятором.

Почему это правило именно такое? Потому что нарушение порождает целый класс багов, начинающихся с одного типа ситуации: пока один кусок кода читает значение, другой его меняет. В однопоточной программе это data race на уровне ссылок (например, итератор по `Vec`, в который кто-то одновременно делает `push`); в многопоточной — настоящая гонка данных. Rust убирает оба случая одним правилом.

Конкретный пример отказа компилятора:

```rust
let mut v = vec![1, 2, 3];
let first = &v[0];          // &i32 — ссылка на первый элемент
v.push(4);                  // ошибка: нужна &mut Vec, а &v[0] ещё жива
println!("{}", first);
```

Компилятор скажет:

```
error[E0502]: cannot borrow `v` as mutable because it is also borrowed as immutable
```

«Не могу заимствовать v как изменяемое, потому что оно уже заимствовано как неизменяемое». Без borrow checker этот код собрался бы и при определённых условиях упал бы на исполнении: `push` мог бы привести к переаллокации `Vec`, после которой `first` указывал бы на освобождённый блок памяти. Use-after-free, в одном потоке, в учебном примере. В Rust его поймали на этапе сборки.

Второе правило, которое следует из первого автоматически: ссылка не может пережить значение, на которое смотрит. Этот контроль называется проверкой времени жизни (lifetime). Большую часть случаев компилятор выводит время жизни сам, без участия программиста. В тех редких случаях, когда не справляется, нужны явные аннотации (`'a`, `'static`) — мы вернёмся к ним в Главе 3.

Эти два правила в сумме закрывают целый класс ошибок, и на простых примерах это видно сразу — но настоящая сила borrow checker раскрывается на конструкциях, которые обычно ломаются молча. Возьмём итерацию по коллекции:

```rust
let mut v = vec!["alice".to_string(), "bob".to_string(), "carol".to_string()];
for name in &v {
    if name == "bob" {
        v.push("dave".to_string());     // ошибка
    }
}
```

То же правило, другая форма: `for name in &v` берёт неизменяемое заимствование `v` на весь цикл, а `v.push(...)` требует изменяемого — компилятор отказывает по той же причине, что и в примере выше.

Borrow checker не запрещает бездумно всё подряд. С 2018 года компилятор Rust использует так называемый non-lexical lifetimes — анализ времени жизни ссылок не по фигурным скобкам, а по реальным точкам последнего использования. Например, такой код собирается:

```rust
let mut v = vec![1, 2, 3];
let first = &v[0];
println!("{}", first);   // здесь последнее использование `first`
v.push(4);                // ок: ссылка first уже больше не нужна
```

Хотя `first` объявлена раньше `push`, компилятор видит, что после `println!` она нигде не используется, и заканчивает её время жизни прямо там. Этот анализ снимает большую часть искусственных ограничений и делает практический Rust заметно дружелюбнее, чем теоретический.

```rust
fn dangling() -> &String {       // ошибка: ссылка пережила бы s
    let s = String::from("hi");
    &s
}                                // s освобождается здесь, ссылка стала бы висячей
```

Без проверки времени жизни ровно такая функция — классическая ловушка: возвращается ссылка на локальный объект, который уже уничтожен. В Rust компилятор отказывается собирать.

Компилятор не делает тебя осторожным. Он делает физически невозможным сказать то, что не является правдой о владении.

Это сильное утверждение, и стоит его проверить на конкретике. «Правда о владении» — это что? Это ответы на три вопроса о каждом значении: кто хозяин, как долго оно живёт, кто имеет к нему доступ и какого типа. Обычно эти ответы либо размазаны по программе, либо вовсе неявны. В Rust они записаны в типах: `String` — владение, `&String` — заимствование на чтение, `&mut String` — заимствование на запись, `'a` — связка времени жизни. Программа, в которой эти типы согласованы между собой, по построению не содержит висячих указателей и не содержит неконтролируемого совместного доступа. Программа, в которой они несогласованы, не собирается.

Это и есть тот сдвиг, о котором был пролог: класс утверждений о памяти, который раньше держался на честном слове, теперь держится на типах. Ты по-прежнему пишешь логические баги; ты по-прежнему можешь неправильно посчитать индекс, забыть условие, выбрать не тот алгоритм. Но конкретный класс ошибок — use-after-free, double-free, висячие указатели, чтение из неинициализированной памяти, гонка ссылок — этого класса ошибок в твоём `cargo build` больше нет.

У метод есть три варианта первого параметра:

```rust
impl Counter {
    fn read(&self) -> u32 { /* ... */ }            // только чтение
    fn increment(&mut self) { /* ... */ }          // изменение
    fn into_total(self) -> u32 { /* ... */ }       // потребление: счётчик после этого исчезает
}
```

`&self` — метод заимствует объект на чтение; можно вызывать сколько угодно раз подряд, можно вызывать одновременно с другими `&self`-методами. `&mut self` — заимствует на запись; пока он работает, никто другой не может ни читать, ни писать. `self` — забирает объект во владение; после такого вызова переменная-источник больше не существует. Это та же иерархия `&T` / `&mut T` / `T`, только применённая к первому параметру методов. Когда ты проектируешь свой тип, выбор между этими тремя — это и есть проектирование контракта: что метод обещает не трогать, что обещает изменить, и что забирает безвозвратно.

## Практика: буфер событий

Соберём что-то конкретное. Кольцевой буфер событий — структура, в которую можно дописывать события и из которой можно читать N последних. Используется везде, где нужна история без неограниченного роста: лог последних запросов сервера, история действий пользователя, телеметрия.

```rust
#[derive(Debug, Clone)]
pub struct Event {
    pub timestamp_ms: u64,
    pub kind: String,
}

pub struct EventBuffer {
    events: Vec<Event>,
    capacity: usize,
}

impl EventBuffer {
    pub fn new(capacity: usize) -> Self {
        EventBuffer {
            events: Vec::with_capacity(capacity),
            capacity,
        }
    }

    pub fn push(&mut self, event: Event) {
        if self.events.len() == self.capacity {
            self.events.remove(0);
        }
        self.events.push(event);
    }

    pub fn recent(&self) -> &[Event] {
        &self.events
    }

    pub fn len(&self) -> usize {
        self.events.len()
    }
}
```

Несколько слов о том, что здесь происходит.

`#[derive(Debug, Clone)]` — атрибут, автоматически генерирующий реализации трейтов `Debug` (можно напечатать через `{:?}`) и `Clone` (можно вызвать `.clone()`). Подробнее про трейты — Глава 3.

`pub` — модификатор видимости. По умолчанию в Rust всё private; чтобы сделать поле или функцию доступной снаружи модуля, нужно явно написать `pub`. Большинство языков открыты по умолчанию. Rust — наоборот. Новый член начинает жизнь приватным, и требуется усилие, чтобы его открыть. Это правильный default.

`impl EventBuffer` — блок с методами для типа. Внутри методы, принимающие `self` (move), `&self` (read-only заимствование) или `&mut self` (изменяемое заимствование). Сигнатура `pub fn push(&mut self, event: Event)` означает: «push требует изменяемого доступа к буферу и принимает событие во владение».

`Self` (с заглавной) — псевдоним типа, к которому относится текущий `impl`. То есть `Self` здесь — это `EventBuffer`. Удобно, когда переименование типа не требует править всё его внутреннее устройство.

Метод `recent` возвращает `&[Event]` — срез событий внутри буфера. Заметь, что мы не возвращаем `Vec<Event>` (это потребовало бы клонирования) и не возвращаем `Vec<&Event>` (избыточно). Срез — лёгкая структура из двух полей: указатель и длина; он живёт ровно столько, сколько живёт `EventBuffer`, и компилятор это знает.

Воспользуемся:

```rust
fn main() {
    let mut buf = EventBuffer::new(3);
    buf.push(Event { timestamp_ms: 100, kind: "click".into() });
    buf.push(Event { timestamp_ms: 200, kind: "scroll".into() });
    buf.push(Event { timestamp_ms: 300, kind: "click".into() });
    buf.push(Event { timestamp_ms: 400, kind: "type".into() });

    for e in buf.recent() {
        println!("{:?}", e);
    }
}
```

`"click".into()` — преобразование `&str` в `String` через трейт `Into`. Эквивалент `String::from("click")`, но короче в записи; внутри происходит ровно то же самое: аллокация в куче, копирование байт.

Программа печатает три события — `scroll`, второй `click` и `type`. Первый `click` ушёл, потому что мы превысили capacity.

Теперь самое интересное: попробуем то, что обычно становится типичной ошибкой.

```rust
let mut buf = EventBuffer::new(3);
buf.push(Event { timestamp_ms: 100, kind: "click".into() });
let snapshot = buf.recent();           // &[Event]
buf.push(Event { timestamp_ms: 200, kind: "scroll".into() });  // &mut self
println!("{:?}", snapshot);
```

```
error[E0502]: cannot borrow `buf` as mutable because it is also borrowed as immutable
```

Тот же механизм на структуре посложнее: `snapshot`, полученный от `recent`, мог бы стать висячим после `push`, если бы внутренний `Vec` переаллоцировался — классический use-after-free. Компилятор поймал это не на ревью и не в проде, а на сборке.

Чтобы получить совместимое поведение, нужно либо не держать ссылку через `push`, либо явно склонировать снимок:

```rust
let snapshot: Vec<Event> = buf.recent().to_vec();
buf.push(Event { timestamp_ms: 200, kind: "scroll".into() });
println!("{:?}", snapshot);
```

`to_vec()` создаёт независимую копию — теперь `snapshot` не зависит от `buf`. Компилятор счастлив, программа собирается, поведение предсказуемо. Цена — одна аллокация и копирование. Она явная и видна в коде; ты сам решаешь, платить её или нет, и это решение принято осознанно, а не по умолчанию.

Можно и иначе. Если задача — посчитать что-то по снимку, не сохраняя его, — достаточно ограничить scope ссылки:

```rust
let last_kind = {
    let snapshot = buf.recent();
    snapshot.last().map(|e| e.kind.clone())
};   // здесь scope блока закрывается, snapshot больше не существует
buf.push(Event { timestamp_ms: 200, kind: "scroll".into() });
println!("{:?}", last_kind);
```

Внутри блока живёт неизменяемая ссылка `snapshot`; за пределами блока её нет, и `push` имеет полное право взять `&mut self`. Это типичный приём в Rust: ограничивать ссылки минимальным блоком, в котором они нужны. Пока пишешь — кажется бюрократией; через неделю замечаешь, что начал думать о коде с большей ясностью, чем раньше: «вот здесь я читаю, вот здесь меняю, и эти два момента не пересекаются».

Покроем буфер тестами:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    fn ev(ts: u64, kind: &str) -> Event {
        Event { timestamp_ms: ts, kind: kind.into() }
    }

    #[test]
    fn capacity_is_respected() {
        let mut b = EventBuffer::new(2);
        b.push(ev(1, "a"));
        b.push(ev(2, "b"));
        b.push(ev(3, "c"));
        assert_eq!(b.len(), 2);
        assert_eq!(b.recent()[0].kind, "b");
        assert_eq!(b.recent()[1].kind, "c");
    }

    #[test]
    fn empty_buffer() {
        let b = EventBuffer::new(3);
        assert_eq!(b.len(), 0);
        assert!(b.recent().is_empty());
    }
}
```

Тесты проверяют два контракта: «при превышении capacity старые события вытесняются» и «новый буфер пуст». Маленький `ev` — фабрика, чтобы тесты не превращались в стену конструкторов. Это привычка, которая окупается, как только тестов становится больше пяти.

→ Приложение F.2 показывает ту же логику владения на уровне популяции организмов: рождение — это выделение, смерть — это освобождение, наследование — это move. Буфер событий и популяция Box2D-существ устроены одинаково; разные слова для одной идеи.

## Финал

Эта глава — техническая на поверхности и философская в основе.

Техническое содержание: ownership, move, borrow, два вида ссылок, главное правило borrow checker, детерминированный `Drop`, методы с `&self` / `&mut self` / `self`. Всё это — конкретные конструкции, которые можно показать в коде, проверить компилятором, измерить на бенчмарке. Они работают, и работают предсказуемо. Если ты прошёл главу до конца и попробовал примеры в `cargo run` — у тебя уже есть рабочий словарь, на котором можно собирать настоящие программы. Не «учебные», не «модельные», а такие, которые ходят в продакшен и не падают.

Под этим — установка, которая в индустрии встречается редко: что код может говорить правду о структуре, которой управляет, и что эту правду можно проверять автоматически, а не на код-ревью и в постмортемах. Тот баг из открытия главы — функция `writer` с глобальным буфером — в Rust не написать. Не потому, что мы его запретили дополнительным линтером. Потому, что в Rust нет способа выразить «я делю эти данные между двумя потоками без синхронизации» — типы не позволяют. Чтобы такое разделение появилось, нужно явно собрать его из конкретных конструкций (`Arc`, `Mutex`, `RwLock`), и каждая из них требует подписать соответствующий контракт; нарушить его, не привлекая внимания компилятора, нельзя.

Borrow checker — не аппарат проверок. Это утверждение, что инженерная корректность начинается с честности о том, кто чем владеет. Один поток, одна функция — здесь это держится без видимых усилий. Что произойдёт, когда потоков станет много, разберём в Части III.
